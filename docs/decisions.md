## 已知限制 / 待办（按优先级）

1. **重启时的续流**：OpenRouter 无状态，除 Gemini 4 long decode（已实现：checkpoint 落盘，重启后在原消息上接着写）外，重启只能重试；`/generation/content` 只能补回断开前已送达的文本（已用于填充被打断的那条消息）。（不做 relay 进程，D18。） 直连官方 API 时：Gemini 4 long decode 和异步任务（视频、GLM-Image）能接着；OpenAI 断流（网络断、连接没被关闭）时从它保存的结果补全（D61），但重启会关闭连接、OpenAI 随即取消，只能重试（background 模式能续，但首字慢约 6 秒，作者决定不用）；Gemini 的 Interactions API 也能续，未实现。
2. **官方直连 provider 都未经真实请求验证**（等各平台的测试 key）：请求格式、事件格式、错误体、计费字段都只按文档和无 key 的探测实现；每个模块的文档注释和测试里列出了待实测的点（如方舟的 `max_tokens` 上限、`encrypted_content` 回传；OpenAI `chat-latest` 是否接受推理摘要；xAI 的事件类型）。
3. 私聊使用 Telegram live draft 流式（仅私聊可用，群里只能 send+edit）。
4. 群内 per-user 提示用 ephemeral message（bot 需是管理员或 15 秒窗口）。
5. **错误录音的补充**：内容审核（OpenRouter 403）和拒答不靠违规提示词去诱发，真实遇到时把原始日志补进 `crates/omni-llm/tests/fixtures/`；流中途的 in-band 错误同理。
6. 未定的小项：图片 `detail` 只在 Responses（OpenAI、xAI）和方舟上发送，Chat Completions（Gemini 等）没有这个字段；effort 可选值按官方档位表与 OpenRouter 目录取交集；`openai/gpt-audio` 的语音输出要走 CC。
7. **大消息编辑的轻重规律**：哪些版式的编辑算重操作还没弄清（rate19），目前保守地全算重；弄清后长回答能更新得更快。
8. **外层折叠显示正在运行的工具**（作者 2026-11-13：之后再加）：模型卡在工具调用上（搜索、代码执行…还没有结果）时，那串推理和工具调用的外层折叠标题也写出正在进行的是什么工具调用，就像正在进行的思考那样；工具调用有了结果（或后面出现了别的内容）就去掉。
